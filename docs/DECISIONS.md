# Architecture Decision Records (ADR log)

The record of dev's foundational decisions: the ones that shape how every consumer runs dev, and that a change would have to reopen rather than quietly revise. Each ADR is immutable once `Accepted`; a revision supersedes it with a new ADR. The README describes what dev does today; this log records why it is that way and what was rejected.

Format: Context → Decision → Consequences → Rejected. Status: `Accepted` unless noted.

---

## ADR-0001 — dev is live infrastructure

**Status:** Accepted. Litigated in [dev#218](https://github.com/d3mlabs/dev/issues/218) — the thread to reopen before changing any of it.

**Context.** dev runs on workstations, on self-hosted runners, in hosted CI jobs, and in the build containers it orchestrates. Each place dev runs is a place a stale dev can run. Hosts already converged on the latest release on every `dev up` ([b835291](https://github.com/d3mlabs/dev/commit/b835291) removed the last self-update throttle so a fix propagates on the next `dev up`), but the build-container image bootstrap left a `brew install dev-core` in the image layer ([fcdbb69](https://github.com/d3mlabs/dev/commit/fcdbb69) and before) — never run by anyone, but a frozen copy that *could* be run by accident, and a permanent question of which dev an image contains.

**Decision.**

- **dev is live infrastructure, not a pinned dependency.** Projects declare no dev version; every machine runs the latest release from the tap. Hosts converge on `dev up`. The rule made for hosts is the rule for every place dev runs.
- **Backward compatibility is the only contract.** Because consumers never pin, a release must keep reading every project artifact its predecessors wrote: `dev.yml`, `dependencies.rb`, and the lockfiles (the reader still accepts the legacy flat lock format for exactly this reason). A change the previous release's files cannot survive is a breaking change and is released as one.
- **The build container is the dependency environment; the image is not a copy of dev.** Image builds install their toolchain with `dev deps install --group build --integration brew` from `build-deps.lock` — the same command, reading the same lock, as the host — and then uninstall dev-core (`bin/docker-install-build-deps.sh`). The tool that ran the install leaves; only what it installed stays — including the formulae dev-core itself depended on (gh, git, rbenv, ruby-build, shadowenv, …), kept deliberately so that provisioning a container's dev pours one formula, not thirty. The image's answer to "which dev does it contain" is "none".
- **Containers match the orchestrator.** The host's dev owns the container's lifecycle, and on every `dev up` / `dev container up` it converges the persistent container's dev-core to its own exact version (`dev version` inside equals outside): one version per host, host and container alike, re-synced after a host upgrade with no manual step. The exact version is not "latest from the tap" — the tap only carries the latest formula, so the install checks the tap out at the commit whose `dev-core` formula shipped that version (`bin/container-provision-dev.sh`) and never falls back to latest silently. A machine with no orchestrating host — a hosted runner — is a host (ADR-0007) and gets the latest release, like a fresh workstation. The inside dev knows it is inside (`DEV_INSIDE_CONTAINER=1`, set by the host on every container it creates) and so never self-updates: the host is the only writer of the container's dev.
- **The writable layer is ephemeral by design.** A persistent container is per checkout and per image tag (`dev-<image>-<workspace_id>-<tag>`); anything that must survive a rebuild (installed deps, caches, the container's Ruby and gems) lives in the data root, never in the layer.

**Consequences.** No per-repo dev version to bump. A release is the only unit of change consumers see, so release discipline (backward-compatible readers, breaking changes called out) carries the whole contract. Image builds depend on the tap at build time (to install the dev that installs the toolchain) and never on a dev inside the image afterwards. The README's "dev is live infrastructure" section is the operative summary of this record.

**Rejected.** Pinning a dev version per image — reintroduces the stale-dev-in-the-image class this record exists to end, plus a bump chore per repo per release. `brew upgrade dev-core` at job start on a dev frozen into the image — a second, slower update path for a copy that should not exist.

## ADR-0002 — Dependencies install where they are consumed

**Status:** Accepted. Milestone 5 of [dev#218](https://github.com/d3mlabs/dev/issues/218).

**Context.** With dev running inside the build container (ADR-0001), one `dev deps install` on the host cannot serve both sides. Gems made it concrete: a `bundle install` on a Mac produces native extensions for darwin, which a Linux container cannot load, and the container has no rbenv Ruby to install them against. File artifacts (`gh` releases, Steam apps, ficsit mods) have the opposite shape: fetched once, platform-neutral or already platform-keyed, and readable from either side through the shared data root.

**Decision.** Each integration type has a scope (`lib/dev/deps/registry.rb`: `HOST`, `CONTAINER` or `BOTH`). The host's `dev deps install` runs the host-scoped types; `dev container up` then runs `dev deps install` inside the container, where the container-scoped types run against the container's own Ruby — a `ruby-build` tree in the shared artifact store, not an rbenv one, activated by a shadowenv guard that only fires behind `DEV_INSIDE_CONTAINER`. `bundler`, `brew` and `cask` are `BOTH` (each side gets its own bundle against its own Ruby); everything else is `HOST`, and the container reads those artifacts through the store. The host-side hygiene hooks (gem skill links, learnings sync) do not run inside: the links land in the mounted project tree and must name the host's paths.

**Consequences.** `dev up` on the host is also the container's install (`dev container up` runs it inside after provisioning dev). The container's Ruby and gems live in the data root, so they survive a rebuild of the writable layer. Two bundles means two installs — necessarily, since native extensions are per platform — but one fetch: bundler's download cache is a store tool cache under the shared data root, so pure-Ruby gems the host fetched are already there for the container (`docs/deps-architecture.md`, transitive-dependency regimes). A `bundle install` on Linux adds `x86_64-linux` to the shared `Gemfile.lock` PLATFORMS — expected, and committed once.

**Rejected.** A host-filter rule ("everything but gems installs on the host") — the plan's original shape; a scope axis names the fact per type instead of encoding it in one integration's exception.

## ADR-0003 — A brew lock has bite on both sides

**Status:** Accepted. Milestone 8 of [dev#218](https://github.com/d3mlabs/dev/issues/218).

**Context.** Brew is a moving registry: `brew install cmake` installs whatever `homebrew/core` has today, so `build-deps.lock` recording `cmake 4.4.3` constrained nothing — a host and an image built a month apart from the same lock got different toolchains, silently. Pinning taps was the known fix and the known cost: a `brew tap` of homebrew-core clones its full history, which is what had kept image builds on brew's API.

**Decision.** Two mechanisms, one per side of the container boundary.

- **Hosts verify (B).** After every brew install — and when the formula was already present — `dev deps install` reads `brew list --versions` and fails unless a keg matches the locked version (brew's own `_N` revision suffix aside). The error carries both remediations, because the two causes need different hands: `dev deps update` when brew's formula moved on and the lock is stale; `brew upgrade <formula>` when the machine is behind. Hosts keep brew's API mode — the verification is the contract, not the install path.
- **Images pin (A).** `dev deps update` records per formula the commit its tap was at (`tap_commit`) and `format` — `bottle` when an `x86_64_linux` bottle exists, `source` when the image build would compile it — and names every build-group formula that would build from source, right where the lock is written. `dev deps install --pinned-taps` checks each tap out at its locked commit with a **single-commit fetch** (`git fetch --depth 1 origin <commit>` into brew's taps layout) and installs under `HOMEBREW_NO_INSTALL_FROM_API=1 HOMEBREW_NO_AUTO_UPDATE=1`, so two image builds of one lock install one toolchain. A lock without tap commits, or one pinning a tap at two commits, fails before anything is pinned.
- **Order of landing.** B ships everywhere first. A is opt-in in the image bootstrap (`DEV_PIN_TAPS=1`) until the single-commit fetch has been measured against a real image build; the default image build installs through the API and verifies like a host.

**Consequences.** A stale lock fails loudly instead of drifting. B bites on existing machines whose kegs are behind the lock on the first `dev up` after it ships — the remediation is in the message. Existing locks carry no `tap_commit`/`format` until the next `dev deps update`; only `--pinned-taps` requires them. Casks are not verified (brew reports no stable version for most).

**Rejected.** Pinning taps on hosts too — a host is a workstation with other brew consumers, and a checked-out core tap would fight `brew update`; verification gives the lock its bite there without owning brew. Cloning the taps for pinning — the history cost that kept A off the table; the single-commit fetch is what makes A affordable.

**Note (2026-10-29, dev#350).** B enforced the lock but never satisfied it: `brew install` ran only for an absent formula, so a keg at another version failed the verification with a remediation for a human (`brew upgrade`), and an ephemeral runner booting a checkpoint whose brew index predates a re-lock has none — the one channel where "a PR that moves a lock installs the difference per run" did not hold. Hosts now converge before they verify. The lock carries every bottle a version publishes (ADR-0004), so the exact bottle for this machine — the tag brew would pour, asked with `brew --cache --formula` — is fetched from the lock's link, checked against the lock's digest (the first enforcement use of that record), kept in the store under brew's bottle file name and poured with `brew install <file>`, which needs no index and goes down as well as up. brew refuses to pour an older keg under a newer linked one, or another version of an opt-linked keg-only formula, so a pour that leaves no locked keg is retried `--force --skip-link`: the project activates its keg by path (ADR-0010), brew's link stays the user's. A version with no bottle for this machine (brew builds it from source; a pin older than bottle records) is converged by `brew update` then `brew upgrade <formula>` — a machine behind the lock heals, a lock behind brew's formula still fails, and the error now carries that one remediation, `dev deps update`. Pinned-taps installs do not converge: the tap at its commit is the install path, and a `brew update` would move it. Rejected: `brew reinstall <bottle>` — it deletes the keg it replaces, which another checkout may lock; `brew version-install` — `brew extract` needs the tap's git history, which API-mode hosts do not have; deciding upgrade-versus-downgrade in dev by comparing versions — brew's ordering is brew's, and the second pour costs one refused invocation only when the first did not take.

**Note (2026-10-29, dev#356).** The pour above never ran: Homebrew 4 dropped `brew install <file>` (the path is read as a tap name) and `brew install --formula <file.rb>` with it, and a core formula copied into another tap is refused (`no_autobump!` is core-only DSL). The one mechanism brew offers for a specific version is the tap checked out at a commit — the pinned-taps install, scoped. Converging now pins the formula's tap at the lock's `tap_commit` (`TapPinner#pin!` remembers what the tap was: its branch, or absent on an API-mode host; a full clone is fetched without shallowing it), runs `brew install <formula>` under `HOMEBREW_NO_INSTALL_FROM_API=1 HOMEBREW_NO_AUTO_UPDATE=1`, retries `--force --skip-link` when brew refuses an older keg under the linked one (as before), and `restore!`s the tap in `ensure` — a developer's brew reads its usual sources again whatever happened. Brew's own bottle fetch and digest check cover what the deleted download did; the lock's bottle records (ADR-0004) stay the provenance they were. A documented side effect: dependencies the install brings in come from the same commit. The `brew update` + `brew upgrade` path remains for a lock without tap commits only. A refusal of the pinned formula — a commit old enough that today's brew rejects its DSL — is the `VersionMismatchError`, carrying brew's first line and the one remediation, `dev deps update`. Rejected: `brew install --formula <file.rb>` and a scratch tap holding the lock's formula files — both refused by current brew (the first "source doesn't exist on disk", the second the core-only DSL); the lock's bottle URL fed to `brew fetch` — fetch takes a formula, not a bottle; a shallow pin left in place — it breaks `brew update` for the user.

**Note (2026-10-29, [dev#355](https://github.com/d3mlabs/dev/issues/355)).** The lock's bite ran one way: hosts and images were held to the lock, but `dev deps update` wrote whatever the writing machine's brew index held, so a re-lock for one added `gh` line on a newer Mac moved `python@3.12` and `cmake` too (cellbound-3d#319). The lock is now also conservative about itself: a brew pin whose declaration did not change keeps the lock's version (the carry-over principle of ADR-0005, extended from the commit to the version — see its note), and the author floats pins deliberately with `dev deps update <name>` or `--all`. Hosts converging to the lock (the dev#350 and dev#356 notes) is what makes keeping a version safe: the kept pin is one the lock can install anywhere, which is also why a pin the lock records no bottle for is the one exception that floats on its own. The A/B mechanisms are unchanged; `pin_taps!`'s refusal of a tap at two commits now has `dev deps update --all` as its remediation, since a conservative re-lock legitimately leaves one.

## ADR-0004 — A lock describes what is published, not the machine that wrote it

**Status:** Accepted. [dev#232](https://github.com/d3mlabs/dev/issues/232), a consequence of ADR-0003.

**Context.** A brew pin carried one `hash`: the SHA256 of whichever bottle the writing machine would download (`arm64_sonoma` on a Mac, `x86_64_linux` on a Linux box). The same `dev deps update` on two hosts wrote two locks for one version. With the build image content-addressed on `build-deps.lock` (ADR-0001), a Linux re-lock that changed no version still changed every brew hash, so every image tag — a rebuild for nothing — and the hash gated nothing: brew verifies its own bottles. The pre-flight that names source-built formulae had the mirror bug, naming a Mac-only formula (`xcodes`) for an image it never enters.

**Decision.** A repository reports every platform a version publishes — for brew, every bottle tag with its URL and SHA256, read once per formula (brew's own info for tap formulae, the public formula API for `homebrew/core`, whose local info lists only this machine's bottle). The Resolver's projection rule gains a third shape: when the declaration names no platform and no target but the version publishes several, the pin carries a `platforms:` block over all of them. Brew pins carry no top-level `hash`. The projection rule lives in the Resolver, where declarations meet versions — a repository never sees declarations, and which targets a pin describes is a property of both. The pre-flight asks `Installer.select` with the image build's own axes (build group, brew, Linux host, CI env) instead of re-deriving the gate.

**Consequences.** A lock is the same bytes whoever writes it, so a re-lock that changes no version changes no image tag. `format` is derived from the same bottle list as the block, so the two cannot disagree. Existing brew pins keep their `hash` until the next `dev deps update`; readers accept both. The block is a record, not an enforcement input — brew still verifies at install (integrity regimes, `docs/deps-architecture.md`); verifying bottle bytes in dev would be a new regime and is out of scope here. `tap_commit` remains the one fact that varies with the writer's brew state, by design: it is what the pin pins.

**Rejected.** Recording only the image platform's bottle — fixes the churn but keeps the lock partial, and a Mac developer's host install would verify against a Linux hash. Keeping the Mac bottle as `hash` beside the block — a hash that gates nothing is dead weight the content-addressed image still pays for. Putting the "record every platform" rule in `BrewRepository` — it would have to produce a pin shape, which is the Resolver's job; the repository reports facts.

## ADR-0005 — A tap's commit moves only when its pins move

**Status:** Accepted. [dev#234](https://github.com/d3mlabs/dev/issues/234). Refines ADR-0004's consequence that `tap_commit` "remains the one fact that varies with the writer's brew state".

**Context.** `tap_commit` (ADR-0003) is brew's `tap_git_head`: the HEAD of the whole tap at `dev deps update` time, not the commit that last touched the formula. `homebrew/core` moves dozens of times a day, so any `dev deps update` on a machine that had run `brew update` since the previous lock rewrote the commit on every core formula with no version, bottle or `format` changed — observed the hour ADR-0004 shipped (four `tap_commit` lines, nothing else). The build image is content-addressed on `build-deps.lock`'s bytes (ADR-0001), and `Lockfile#lock` writes both lockfiles from one resolution, so bumping a gem rebuilt and republished the build toolchain's image and every machine pulled it, for a toolchain that had not changed. ADR-0004 made the lock independent of *who* writes it; this is its dependence on *when*.

**Decision.** `tap_commit` is provenance, not an install fact: it names *a* commit of the tap at which the pin's formulae are what the lock says, and the previous lock's commit satisfies that whenever the tap's pins have not changed. So `dev deps update` carries it: after `Resolver#resolve` and before `Lockfile#lock`, `TapCommitCarryover` reads the lock on disk and, for every brew tap none of whose pins changed — same formula set; same version, hash, group, scope and metadata but `tap_commit` — writes the previous commit onto the resolved pins. A tap where anything moved takes today's HEAD on every one of its pins: a pinned install checks a tap out once (`pin_taps!` refuses two commits for one tap), so the unit of change is the tap, across both lockfiles. The rule is a policy of the lock being written and lives in the `dev deps update` builtin; the Resolver stays a pure function of the declarations and the universe and never sees the previous lock. A previous lock with no commit, two commits for one tap, or pins in an older shape carries nothing — today's HEAD stands.

**Consequences.** A re-lock that changes no formula in a tap writes identical bytes for that tap whenever and wherever it runs; `build-deps.lock` diffs mean the toolchain moved again, and the build image rebuilds when it does. A version bump of one core formula moves `tap_commit` on every core pin in one diff. The `platforms` block is part of "unchanged", so a revision bump (bottles rebuilt at the same version) moves the tap; a bottle-less tap formula is compared on version alone, which is also all B can see — a formula edited without a version bump is invisible to the lock, as before. An app-group brew formula bump moves the core commit in `build-deps.lock` too (one commit per tap across both files); gems and non-brew artifacts, the common re-lock triggers, do not.

**Rejected.** Dropping `tap_commit` from the content tag — under `--pinned-taps` it is an image input, and `content_tag` hashes bytes, not a parsed lock. Recording it only when pinned taps are enabled — the lock is universal; a pinned install of a lock without commits fails by design (ADR-0003). A per-formula "last commit touching the formula file" — stable by construction, but core is API-mode on hosts: no git tap to ask, and the formula API does not expose it. Threading the previous lock into `Resolver#resolve` — a pure solver gains an input every test must fake. Comparing on version alone — misses revision bumps and bottle-set changes, which change what a pinned image pours. Carrying per formula — finer, but it hands `pin_taps!` two commits the first time one formula moves. Carrying per tap *per lockfile* — would let `deps.lock` and `build-deps.lock` disagree on a tap's commit, which a host's pinned install (reading both) refuses and whose remediation, `dev deps update`, would then not heal. A generic `Repository#provenance_keys` seam — one abstraction for one key; reopened if a second carried fact appears.

**Note (2026-10-29, [dev#355](https://github.com/d3mlabs/dev/issues/355)).** The principle — a re-lock that changes no declaration should change no pin — extends from the commit to the version, and the unit of carry-over moves from the tap to the pin. `TapCommitCarryover` is replaced by `PinCarryover`: a brew pin (formula or interpreter; casks pin no version) whose declaration did not change — same tap, group, host and env, and the locked version still satisfies its constraint under the integration's scheme — keeps the lock's version, hash, bottle set and `tap_commit`, provided the lock records bottles for it (ADR-0004; the host converges by pouring them, dev#350): `bundle install` against an existing `Gemfile.lock`, which is what plans#50 D3 always meant for the registries dev drives itself. The author floats pins deliberately — `dev deps update <name>…` floats the named declarations and the pins their integrations need (`bundle update <gem>`), `--all` floats everything (`bundle lock --update`) — and a changed declaration floats its pin; a pin the lock has no bottle for floats as the one move not asked for, named in the output with its reason. A floated pin that resolves to the very same facts keeps its commit, as before. **What this supersedes above:** "the unit of change is the tap". A tap whose pins moved at different times now carries several commits, which a pinned install still refuses (`pin_taps!`) — with `dev deps update --all` as the remediation, which re-resolves every pin at one HEAD. The "Carrying per formula" rejection stands as a trade accepted: finer carry-over costs the single-commit invariant on a lock that was re-locked piecemeal; converging images through the tap at each pin's own commit is dev#356's. A subset re-lock also carries every non-brew pin it did not float verbatim from the lock on disk, so the tool-owned channels (bundler) and the registries dev drives agree on what "update one thing" means. Rejected here: resolving only the named declarations — the lock must still describe the whole manifest, and a full resolution merged against the previous lock does that while a filtered one would drop the pins of a removed line only by accident; threading the previous lock into `Resolver#resolve` — rejected above, still; deciding "still published" by asking brew — the lock's own bottle record is the fact the host installs from, and asking the index is what made the re-lock drift.

## ADR-0006 — The build container runs as the host's user

**Status:** Accepted. [dev#236](https://github.com/d3mlabs/dev/issues/236), a consequence of ADR-0002.

**Context.** Dependencies install where they are consumed (ADR-0002), so the container writes the host's data root — its Ruby, its gems, the shared caches — through the `/var/lib/dev` bind mount, as whatever user the image runs as (`USER builder`, uid 1000, in cellbound-3d's Dockerfile; snappy's image stays root). dev starts the service container with no `--user`. Where the host's user is not uid 1000 — the hosted runner `ue-engine-hosted` runs as 1001 — the mount is owned by a uid the container's user is not, and the first write inside (`ContainerRuby#build!` making `/var/lib/dev/ruby`) fails with `EACCES`: every containerized job on that runner failed from the first release that provisioned Ruby inside, and a consumer workflow had grown a `chown -R 1000:1000` step before `dev test-game` to make the project tree writable from inside, plus two "reclaim ownership" steps to make it readable again outside. Where the ids match (a workstation at 1000) or the mount ignores them (a Mac's virtiofs is writable by any uid) nothing was wrong, which is why it went unnoticed.

**Decision.** The image's user takes the uid and gid that own the mounted data root — the host's user — before anything inside writes it. `Dev::ContainerUserAligner` runs first in `dev container up`'s in-container provisioning, for persistent and cold containers alike, behind a **behavioural gate**: one exec asks the container whether its user can write `/var/lib/dev` (plus its ids and the mount's owner). Writable — nothing happens. Not writable — `bin/container-align-user.sh` runs as root inside: the user's `/etc/passwd` entry and its group's `/etc/group` entry take the owner's ids, then what the old uid or gid held on the container's root filesystem is re-owned (`find / -xdev`: the whole filesystem by old id, not a path list, so Linuxbrew's prefix-ownership check and anything else the image created for that user stay consistent; `-xdev` keeps the sweep off the bind mounts, which are the host's; regular files inside Linuxbrew's Cellar are left at the old ids — on an overlay filesystem every first chown copies the file up, kegs are most of the image's bytes, and Homebrew never writes into a poured keg, only adds and removes whole ones under directories that are re-owned). A root-owned mount (the engine created the host directory) is handed to the container's user instead. `usermod` is not used: it refuses while the user owns a process, and pid 1 is that user's `sleep infinity`; editing the files directly is what `usermod` would do, and `docker exec` resolves the image `USER` name against them at exec time, so the next exec runs as the new uid. The persistent container keeps the change in its writable layer, so the steady state is one probe; a cold container redoes it, like everything else it provisions.

**Consequences.** Every bind mount — project, data root, engine trees — is writable from inside, and what the container writes belongs to the host's user outside; consumer workflows drop their `chown` steps. `dev up` on a matching host or a Mac is one more `docker exec` and no change. The realign is a one-time `find` over the container's root filesystem (seconds on a toolchain image). It relies on the Dockerfile's `USER` being a name (`USER builder`): a numeric `USER 1000` would keep `docker exec` at 1000 after the files changed. An image that stays root writes any mount and is never touched. Nothing runs as root for lack of a better idea: the two root execs do exactly the ownership work and nothing else.

**Rejected.** `docker run --user <host uid>` — the uid has no passwd entry in the image, so `$HOME` resolves to `/`, Linuxbrew refuses a prefix it does not own, and everything the image prepared for `builder` is unreadable; it would also change the container's identity per host, defeating the content-addressed tag. Baking the host uid into the image (`ARG UID`) — one image per host uid, a rebuild per runner, and the tag no longer a function of the lock. `chown -R` of the mount to the image's uid — what the consumer workflow did; it makes the host's own files foreign to the host and needs an undo step per workflow. Gating on platform or environment (`CI`, Linux, "hosted runner") — a guess where a question is available; `test -w` asks the only fact that matters and is right on every host by construction.

## ADR-0007 — The build container exists for a platform the host is not

**Status:** Accepted. [dev#272](https://github.com/d3mlabs/dev/issues/272), part of [plans#48](https://github.com/d3mlabs/plans/issues/48).

**Context.** A project's `build.container` names a Dockerfile whose first line is `FROM --platform=linux/amd64 …`: the environment is a Linux x86-64 toolchain, and on the Macs that develop the project `dev up` builds that image and every `container:` command runs inside it. The same `dev up` on a `linux-x86_64` runner did the same thing: an engine, an image pull or build, a persistent container, the container's dev converged, the container-side install — twenty minutes of bootstrap on cellbound-3d's hosted Tests job before a test ran — to run Linux commands on a Linux machine. The repo also shipped a composite action, `hosted-up`, for jobs written as `container: image: <tag>`: it declared `DEV_INSIDE_CONTAINER=1` from a workflow, installed dev inside at latest, and restored the store from the Actions cache — a third shape ("inside, but nothing made it") with its own install path, cache shape and documentation, kept alive only because the host path on the same platform was too slow to use.

**Decision.** dev has two states, on a host or inside something the host made, and a bare machine is the host state. Whether a host uses the build container is decided by one fact, read from the Dockerfile the project already has: the environment's platform (`Dev::EnvironmentPlatform`, the first `FROM --platform=`) compared with the host's (`Dev::Platform.current`). They differ — `dev up` brings the container up and `container:` commands run inside it, as before. They match — `dev up` installs the whole lock on the host (the `build` group included; the host scope has no default exclusion) and touches no engine, image or container, and `CommandRunner` runs `container:` commands directly in the project's shadowenv. The one exception is the publisher designation, `DEV_PUBLISH_IMAGE=1`, which is unchanged in meaning and gains a shortcut: a host on the environment's platform with it set resolves the content-addressed tag and makes sure the registry holds it — `docker manifest inspect` first, a build and push only on a miss, nothing pulled on a hit — and still runs nothing in a container. `hosted-up` is deleted; a hosted job is written like any other machine: install dev, `dev up`, the project's commands.

**Consequences.** On a same-platform runner the bootstrap is the host install from the lock — what a machine image can then snapshot, so a warm hosted runner is the image taken after `dev up` and nothing else. Until the toolchain installs into the store ([dev#275](https://github.com/d3mlabs/dev/issues/275)), what the Dockerfile layers install outside Linuxbrew (msvc-wine, the Wine prefix) is not in the lock and so not on a same-platform host: a `dev package` that needs it runs where that half is preinstalled, as docker is today. The Dockerfile stays the environment's definition and the build image stays the one image the project publishes; a Mac's `dev up` is unchanged. A Dockerfile without a literal `FROM --platform=` declares no platform, so the host never matches and the container is always used — the conservative reading.

**Rejected.** A third state, "inside, but nothing made it" (`hosted-up`, a marker set by a workflow) — a second install and cache path for one shape, and a container boundary where there is none. Dropping the container when "no engine" or "no docker" is observed — stock hosted images ship docker with the daemon running, so the fact is not observable there, and removing docker from the machine contradicts `dev up` bringing the machine up, docker included. A separate verb for "run on the host" — `dev up` already knows when to bring the container up; the rule generalises to CI rather than CI getting its own verb. A per-repo Tests-only subset image — dev maintains one build image per repo.

**Note (2026-10-25, [dev#307](https://github.com/d3mlabs/dev/issues/307)).** The rule is asked **per image**, not per project. A project may pin several `image` blocks and each command names its own with `runs_on:`; the platform compared with the host's is the command's image's (`EnvironmentImage#dev_platform`, the pin's — the Dockerfile read survives only for the deprecated path), so `CommandRunner#placement` and `dev container up` answer it image by image: one host can run one image's commands directly and another's in a container. "One build image per repo" above is superseded by "one image per environment the repo declares"; what the rule decides is unchanged.

**Amendment (2026-10-25, [dev#308](https://github.com/d3mlabs/dev/issues/308)). The host rule replaces the platform rule.** The one fact is no longer "is the host's platform the image's?" but "**was this host provisioned from the image?**" — the image build writes `/etc/dev/environment` (`name=<image>`, `digest=<the generated Dockerfile's SHA-256>`; dev#277), and a host runs an image's commands natively exactly when its marker equals the lock's pin, same name and same digest, and inside the image otherwise (`Dev::HostEnvironment` reads the marker, `Dev::HostRule` answers per image for `CommandRunner#placement`, `dev container up` and `dev up`). Platform is one of the things the digest covers, so a Mac fails the comparison as it did — but so does a Linux box on the image's own platform that was never imaged from it. A container dev made passes: it was provisioned from the image. **Drift** — the marker names the image under another digest — is "not provisioned": `dev up` names both digests and the host's commands run inside the lock's image until whoever owns the host's lifecycle re-images it; dev never converges a host's OS toward the lock (converging cannot remove what a block dropped and turns "provisioned from X" into "X plus history", the hand-made state this removes). Inside a container that has drifted the same comparison is an error (`HostRule::ContainerDriftError`, pointing at `dev container reset && dev up`): a container cannot replace itself. The two states and the publisher shortcut stand; what changes is what the host state does with an image it was not made from.

*Why the platform rule gave way.* It left the OS floor an undeclared input on every Linux host: Wine, `winbind`, an i386 userland, the editor's X/GL/ALSA libraries were filled by hand — snappy's runner-setup block, cellbound-3d's `dev-box-setup`, a WineHQ apt block in two workflows — and nothing checked that what a host had was what the lock named. The **bootstrap argument above is withdrawn**: the twenty minutes it measured were the toolchain-era image (the lock inside the image, re-minted and re-pulled per bump) plus a container-side install duplicating the host's into a second data root — and neither exists since ADR-0008 made the image OS-only and dev#277 made it a pinned base plus one apt layer; on Linux the container now reads the host's own data root (ADR-0008's Linux variant, below), so running inside installs nothing twice. The rejected "marker set by a workflow" stays rejected: this marker is written by the image build and states how the host came to be, true alike for a cloud worker baked from the image, a WSL distro imported from it, and a container dev created. *Reversal condition:* if running inside costs a hosted job more than the OS provisioning it removes (~1m37s per PR push, plans#49), native on hosted returns as a measured exception. The deprecated Dockerfile path has no marker and keeps the platform rule until [dev#311](https://github.com/d3mlabs/dev/issues/311) deletes it with the path.

## ADR-0008 — A data root belongs to a build host

**Status:** Accepted. Shaped in [plans#48](https://github.com/d3mlabs/plans/issues/48) (2026-10-21); implemented through [dev#275](https://github.com/d3mlabs/dev/issues/275) (the container's data root), [dev#277](https://github.com/d3mlabs/dev/issues/277) (the Dockerfile as a base image) and [dev#192](https://github.com/d3mlabs/dev/issues/192) (the build-host seam and its sync step). Supersedes ADR-0002's shared root; its scope axis went with it (note of 2026-10-21 below).

**Context.** ADR-0002 put every installed artifact in one data root per machine, the host's, and bind-mounted it into the build container at `/var/lib/dev`, on the premise that file artifacts are "readable from either side through the shared data root". That premise has expired. Since the platform rule (ADR-0007) a Linux host never enters the container, so the mount exists only on a Mac; and since cellbound-3d's Mac-native editor (its ADR-0020) the Mac side reads a Mac engine (`group :editor, host: :darwin`), so nothing on the Mac opens the Linux engine, the Linux toolchain or the container's gems. The Linux half of a Mac's data root has exactly one reader, and it sits on the far side of a VM boundary: a bind mount on a Mac is virtiofs over APFS — every `stat`/`open` a round trip to macOS, every name case-folded. Measured on `Engine/Source` (63,902 files) from inside the container, warm: `find` 1,545 ms over the mount against 128 ms on a Docker named volume on the VM's own ext4 disk; opening and reading 27,716 headers 5,152 ms against 340 ms; opening every file 2,785 ms against 279 ms — ten to fifteen times per file operation. In absolute terms that is sub-second on OpenCell's cross-compile (no measurable difference end to end: 63/48/40 s configure/build/incremental either way) and on the order of a minute on a full game-module compile, against builds that x86 emulation measures in tens of minutes; the cost is real and secondary. The semantics are not secondary: the msvc-wine toolchain tree lays lowercase symlinks beside mixed-case originals (`vc → VC`) and does not extract onto APFS at all ([unreal-engine-build-base#3](https://github.com/d3mlabs/unreal-engine-build-base/issues/3), 2026-10-20), so the Mac's container cannot be given the toolchain through the shared root as ADR-0002 assumed. The uid realignment of ADR-0006 and the container-side `--except build` default both exist to reconcile two owners of one directory. Elsewhere the shape is settled: Bazel's remote execution fetches a hermetic toolchain into each worker's own cache; Epic's AutoSDK is a self-contained SDK tree synced onto each Horde agent; Chromium's CIPD installs platform-keyed packages per host with a marker file per install; nix on macOS gives its `linux-builder` VM its own `/nix/store` and talks to it as a remote builder; the devcontainer guidance for Macs is to clone into a named volume. Nobody serves a toolchain across a VM boundary.

**Decision.** A build host is a (machine, platform) pair, and each build host owns the data root for its platform on its own disk. A Mac is one (darwin: Xcode, Blender, pip, the Mac engine, in `~/.dev`). The Linux container a Mac runs is another: its data root is a Docker named volume on the VM's disk, mounted at `/var/lib/dev`, written by the container's own `dev up` from the full linux lock — the `build` group, the gh trees, the gems — with nothing excluded and nothing bind-mounted in from the host. The box and a hosted runner are build hosts as they already were. Consequently the container is a remote that happens to be local: the build-host seam of dev#192 has one sync step for every adapter — a snapshot sha of the working tree (tracked and new files, through a temporary index, the branch untouched) pushed to a hidden ref on the project's GitHub remote, which the build host fetches and checks out in its own workspace — and the local container uses that same step and no other. The checkout is not bind-mounted either: `/project` as a mount is gone, and the container's workspace, like its data root, lives in the VM. What comes back is the artifact (`dist/`), fetched the way it is fetched from any remote. The image carries only what a toolchain tree cannot — the OS, Wine, the `builder` user: the base image of unreal-engine-build-base — and no lock is an image input.

**Consequences.** A dependency bump is `dev up` on each build host and never a re-mint; the content-addressed image tag loses its reason (dev#277). The APFS collision, the ADR-0006 realignment of the data root and the `--except build` default all stop applying: one owner per directory. The container needs `gh` auth for the private releases it now fetches itself (it already needed it for the engine) and a GitHub remote to fetch snapshots from — a Mac with no network cannot build a *new* snapshot in its container, though an already-fetched one rebuilds offline; the local adapter gives up its claim to be the offline path and keeps its place as the adapter for a machine with no box or hosted access. `dev deps path gh <linux tree>` on a Mac host has nothing to answer and says so; the build scripts that ask run inside. The colima disk grows by what the Linux data root weighs (the engine is 66 GB installed) and `colima delete` discards a cache the next `dev up` refills, as a hosted checkpoint does when it expires. Hidden build refs accumulate and are pruned on a retention rule. The Mac's dominant build cost, x86 emulation under Rosetta, is untouched by any of this; that is why the box and hosted runners are the default build hosts and the local container the fallback.

**Rejected.** Keeping the shared root and fixing its symptoms one by one — a sorted archive and `tar -k` for the case collision, a case-sensitive APFS volume for `~/.dev`, the brew prefix bind-mounted at its own path — each repairs the shared-root premise instead of noticing it expired, and none removes the boundary. Putting the data root back into image layers — a re-mint and a multi-gigabyte push per bump, one copy per repo instead of one per host; the reason the store exists. Bind-mounting the checkout with nested volumes for `Intermediate/`, `Binaries/` and the DDC — keeps a second transport alive for one adapter, and the measurement says the checkout's share of the cost is not where the time goes. A bare repository inside the VM so the snapshot push skips GitHub — a second transport and a second auth story to save seconds against a multi-minute build.

**Note (2026-10-21, dev#275).** ADR-0002's scope axis (`HOST` / `CONTAINER` / `BOTH`) collapses with the shared root it described. The axis answered "which of the two owners of one data root installs this type"; with one owner per data root the answer is always "the build host running the install", so the registry has one integration set, `dev deps install` runs it on every build host against that host's own data root, and the container-side `--except build` default is gone. What ADR-0002 keeps is the platform fact — each side installs its own Ruby, gems and brew bottles — which the lock's `host:` filter already states per dependency.

**Amendment (2026-10-25, [dev#308](https://github.com/d3mlabs/dev/issues/308)). The Linux variant: the container's data root is the host's, bind-mounted.** Under the host rule (ADR-0007 as amended) a Linux host not provisioned from the image runs its commands inside the image — the case the Context above said "never" happens — so the premise "a Linux host never enters the container" has expired in its turn. What this decision measured and rejected was serving a data root *across a VM boundary*: virtiofs over APFS, case folding, a toolchain that would not extract. A Linux host has no boundary — docker-ce on the host's own ext4 — so the argument does not reach it, and "one owner per data root" is satisfied by the simplest form: the host's data root bind-mounted into the container **at its own path** (`-v /var/lib/dev:/var/lib/dev`; an overridden `DEV_DATA_ROOT` mounts at its own path too, and the inside `DEV_DATA_ROOT` names the same string), so every absolute path the store embeds reads the same from both sides, one copy, nothing installed twice — the container's `dev deps install` is a probe over a store the host just filled. The named volume stays the Mac's form, for the reason this decision gives. The Linuxbrew prefix is a named volume on both: a Linux host has no prefix to lend at `/home/linuxbrew/.linuxbrew`, and bottles refuse a symlinked one. ADR-0006's user alignment covers the uid cases, as it did for a root-owned volume.

For the mount to be the same from every account, the Linux root had to stop being per-user: `Dev::DataRoot` on Linux defaults to **`/var/lib/dev`** — FHS's place for a program's variable state, user-independent, and the path the container used already — whether or not the directory exists (`DEV_DATA_ROOT` stays the override). UBT's build state is warm only at the absolute path it was compiled at, venvs and binstubs embed theirs; under `~/.dev`, `jpduchesne` on the box, `runner` on a hosted machine and `builder` in the container each compiled one tree at a different path. A default rather than an env var because a default needs nothing to be present in every process context (runner `.env` files, `.bashrc`, ssh, the image), where a missing variable silently installs 100 GB under `~/.dev`. `dev up` on a Linux host whose root is absent creates it, owned by the invoking user at 0755, through `PrivilegedSteps` (`sudo -v`, then one `sudo install -d -o <user> -g <group> -m 0755 /var/lib/dev`; headless without passwordless sudo it refuses with the command spelled out, docker-ce's contract) and moves `~/.dev` into it by rename, every entry except `state`, skipping what the root already has (`DataRootMigration`, the Mac bootstrap's migration extracted). A root that exists but is another identity's is named with the `chown` and never re-owned; who should own a shared root on a multi-account box is [dev#310](https://github.com/d3mlabs/dev/issues/310). The checkout stays bind-mounted until dev#192's snapshot step reaches the local adapter.

**Amendment (2026-10-27, [dev#310](https://github.com/d3mlabs/dev/issues/310)). The host identity rule: a build host's jobs run as a user that is not the operator, and the data root is shared between them.** The dev#308 amendment left "who should own a shared root on a multi-account box" open; the answer follows from what a job holds. A job on a Linux box runs as the OS user its runner service runs as, and *everything* that user has is the job's: with the five services on the box running as the operator, every job — a fork-free private repo's PR included — ran with the operator's `gh` login (admin on twenty repos, `admin:org`), its `~/.ssh`, its home. The separation is by **OS user**, not by GitHub account alone: jobs run as a dedicated **runner user** (`runner`) whose only credential is a **machine user's** classic PAT in its `gh auth` (read on the repos the jobs fetch and the floor package, write nowhere — `d3mlabs-buildhost`, a seat, not a GitHub App: an App's hour-long tokens would need a token source in dev that re-mints across a 62-minute release, and the only thing the App buys is the seat); the operator keeps a normal login in a home the runner cannot read, and still registers runners, because registration needs admin. What a job must *write* it writes with its own `GITHUB_TOKEN` (`contents: write` on the publisher's release job, `GH_TOKEN` on the publish step only — `ContainerGithubToken` already prefers a `GH_TOKEN` the env names), never with the host identity. Hosted runners keep per-job App tokens: a host with no home holds no credential at rest, and that is right for it. *Addendum (2026-10-29, [dev#351](https://github.com/d3mlabs/dev/issues/351)):* the App token does not reach the registry — GHCR refuses installation tokens for every operation — so a hosted job names its own `GITHUB_TOKEN` as the registry's credential in `DEV_REGISTRY_TOKEN`, and `GH_TOKEN` stays the releases'. Two tokens on one `dev up`, each doing the one thing it can; dev infers neither.

Consequences, all in dev so that adding a runner stays "check out, `dev runner register`": the rule lives in **`dev runner register`**, not in a flag the operator remembers — on Linux it converges the runner user (`Dev::RunnerUser`: created if absent, in `docker` and `dev`, no password, no sudo; `--as` renames it) in the same sudo session as the data root, refuses to enroll until that user has a `gh` login (printing the one command, `sudo -iu runner gh auth login --with-token`), checks that login's **reach** over the checkout's lock (`Dev::HostReach`: every `gh` pin's repo, every image's floor package, probed as the runner user; a miss is the command's message with the grant, not a red run an hour in), then enrolls as it (`RunnerSetup as_user:`: `config.sh` under `sudo -u`, the dir under its home, `svc.sh install runner`); an enrollment running as anyone else is drift and takes the existing retire-and-enroll-fresh path, so re-running `register` in each checkout *is* a box's migration. **`dev runner register --help`** carries the three-identity table (who mints, who owns, who installs); **`dev runner status`** reports who each enrollment runs as, the host identity and its token's expiry, and the reach. The **data root** is one tree for two writers — the store embeds absolute paths and warmth is path-bound, so it cannot be per-user — shared through a group: `<user>:dev 2775`, owned by whoever ran `dev up` first (a group granted this minute is not in this login's credentials until the next; the owner writes regardless), setgid, group-writable, an existing single-owner root converged in place (`chgrp -Rh`, `g+rwxs`/`g+rw` down the tree, `secrets-<uid>` pruned) and never re-owned. The group's write bit holds only if what each writer creates is group-writable, and that is the creating process's umask alone — a POSIX default ACL is *intersected with* the requested mode and cannot override `022` — so **dev's own process umask is `002` on Linux** (`Dev::SharedUmask`, first thing in `bin/dev`, inherited by every child on the host and in the container), and neither the login's umask nor the runner unit's needs configuring. ADR-0006's alignment changes target on a Linux bind mount: not the mount owner's ids (the runner user's container would write the root as the operator and could not write its own checkout) but the **host caller's uid in the root's group**, so `/project` is the caller's and the root is the group's, like the host's own writes; the volume rule stands on a Mac. macOS is unchanged throughout: the service is a per-user LaunchAgent and the agent user (plans#26) is the second identity there — this amendment adds on Linux the layer ai-flow assumed was there. Rejected: `chown -R runner` on the root (the operator is the second legitimate writer, not an intruder); two data roots (two cold trees at two paths; the base is 20 GiB and warm only at its path); a default ACL (see above); `root:dev` (the first `dev up` could not migrate `~/.dev` into a root it is not yet, by login, in the group of); moving an enrollment between homes (the runner's `bin`/`externals` are absolute symlinks into the old home; the warmth is in the shared root, not in `_work`).

**Note (2026-10-29, [dev#361](https://github.com/d3mlabs/dev/issues/361)). The macOS variant's brew edge must match the command dev runs.** On a cooperative Mac (plans#26) the job identity is the hidden agent user and the brew prefix stays the operator's, so `Dev::Deps::BrewIntegration` escalates brew writes with `sudo -n -u <owner>` against the one rule the agent host bootstrap writes: `<agent> ALL=(<owner>) NOPASSWD: <prefix>/bin/brew` (`8da3035`). When the download cache moved into the store (`ce58ae3`) the escalated argv became `sudo … env HOMEBREW_CACHE=… brew …` — the `env` form chosen so the variables survive sudo's `env_reset` — and sudoers matches the *command*: `env`, never brew. The edge could not match, `sudo -n` refused, and dev's remediation named a re-register that would have written the same unmatchable edge. The fix keeps brew in sudo's command position: the environment rides as sudo's own `VAR=value` assignments, the executable is `<prefix>/bin/brew` by path (the agent's PATH is no promise), `brew tap` takes the same path, and the edge carries `SETENV`, which is what admits the assignments — no widening of substance, since brew as the owner already runs arbitrary code as the owner. A sudo refusal of the assignments (a drop-in from before) is the same remediation, `dev runner register`. Rejected: granting `/usr/bin/env` (a grant to run anything, with no brew in the rule); `--preserve-env` (needs the same `SETENV`, and carries the calling process's environment, not the per-write pinned-taps variables); `HOMEBREW_CACHE` in the owner's `brew.env` (a per-store choice made a per-user global; cannot carry per-write variables); an `env_keep += HOMEBREW_*` Defaults (wider than one rule, still no per-write assignments).

## ADR-0009 — The store owns placement

**Status:** Accepted. [dev#271](https://github.com/d3mlabs/dev/issues/271), part of [plans#48](https://github.com/d3mlabs/plans/issues/48) wave 2.

**Context.** Three DSL verbs — `gh`, `steam`, `wwise` — took an `install_dir:` the project chose, and the string travelled: into the pin's metadata, into the lock, and from there into `TreeKey.base` for the install, `dev deps path` for the read, `CacheGc` for the prune set, and `BuildContainer.resolve_versioned_volumes` to reverse-match a `dev.yml` volume's host path onto a locked tree. Five readers agreeing on a directory the project typed. The two other tree families in the data root already derived their base from identity — `ContainerRuby` under `~/.dev/ruby` and `~/.dev/gems`, blobs under `cache/<integration>/<name>-<version>-<hash>` — and the asymmetry showed as drift: cellbound-3d and snappy both said `gh "UnrealEngine"` for two different repos, which only did not collide because each had typed a different directory; cellbound-3d and unreal-engine both said `gh "MsvcWineToolchain"` for the same release and shared one tree on the box only because each had typed the same one. Under ADR-0008 nothing of the host's data root is mounted into a container, so the volume reverse-match had no volume left to match; it was dead code that kept the lock a `BuildContainer` input.

**Decision.** The integration derives a tree's base from the package's identity, and nothing else knows it: `~/.dev/gh/<owner>/<repo>`, `~/.dev/steam/<app id>`, `~/.dev/wwise`, each then keyed by version as before (`<base>/<version>/…`, immutable, marker-stamped). `Integration.tree_key(dep)` is the one place the key is built; `Accessor` (`dev deps path`) and `CacheGc` ask it. `install_dir:` is removed from the three verbs and refused with the migration spelled out (`GroupDSL::InstallDirRemovedError`) — not accepted-and-warned, because the override is the drift being removed. `BuildContainer` stops reading the lock: `resolve_versioned_volumes`, `build_contexts_from_lockfile` and `build!`'s `build_contexts:` are deleted; a `dev.yml` volume mounts exactly as written. No platform segment for these three trees: a data root already belongs to one (machine, platform) and the lock's `host:` filter keeps a linux tree out of a darwin root; `TreeKey.platform` stays for `ContainerRuby` until [dev#269](https://github.com/d3mlabs/dev/issues/269).

**Consequences.** A breaking minor (ADR-0001). dev cannot find a tree at a path the manifest no longer names, so trees already on disk move once by hand — `mv <old install_dir>/<version> ~/.dev/<integration>/<identity>/` — or are fetched again by `dev up`; a hosted checkpoint and a Mac's container volume re-fetch (one cold engine install, ~7 min measured). A tree left at the old path is reclaimed by hand, never by gc: gc prunes only bases the project's lock names, and the old base is in no lock. Two projects that lock the same release now share one tree structurally; two that alias different repos under one name cannot collide. Enumerating `<root>/<integration>/*` for bases no lock names is safe only with a cross-project view of what is locked (two projects share the box's data root) and is recorded as [dev#286](https://github.com/d3mlabs/dev/issues/286), not done here. Consumers: cellbound-3d#285, unreal-engine#15, snappy#121 drop the option and re-lock the day the release is cut.

**Rejected.** Keeping `install_dir:` as an optional override with the identity base as default — two sources of truth for one directory, the drift this removes. A name-keyed base (`~/.dev/gh/<name>`) — the name is the project's alias, so the two-projects-one-name case collides and the two-names-one-release case duplicates, both of which the issue names as the reason for the change. A one-release "adopt from the old path" shim — needs the old path, which is exactly what the manifest stops carrying; all three consumers are ours and move together, so lockstep is cheaper than a shim with its own retirement.

## ADR-0010 — The verb follows the channel

**Status:** Accepted. Decisions 1 and 2 of [plans#50](https://github.com/d3mlabs/plans/issues/50) (2026-10-23), which supersedes [plans#48](https://github.com/d3mlabs/plans/issues/48). Consumer-facing statement: [deps-channels.md](deps-channels.md).

**Context.** dev grew one DSL verb per channel it met — `gem`, then `brew` because it was the one formula syntax with prebuilt bottles on both a Mac and Linux CI and dev itself already shipped through the tap, then `gh`, `cmake`, `steam`, `ficsit`, `luarocks`, `pip`, `xcode`, `wwise` — and the tap grew formulae as needs arose: `wwise-cli` because we wrote it, `clang-format@18.1.8` lifting a PyPI wheel, `powershell@7.4.0` lifting a GitHub `.deb`, `axslcc` lifting GitHub tarballs, each the right call when brew was most of what dev had. Two proposals in 2026-10 forced the question of a rule: an `apt` type ([dev#284](https://github.com/d3mlabs/dev/issues/284), withdrawn) and a `:ruby` integration with a ruby-build install path ([dev#269](https://github.com/d3mlabs/dev/issues/269)). Elsewhere the question is settled by shape: a dependency has an identity and version, a *channel* its bytes come from, a *shape* on disk (immutable version-keyed tree, mutable workdir, tool cache, OS state) and a *scope*; how it is reached — PATH, an environment variable — is an activation step any shape admits, which `XcodeIntegration` (`DEVELOPER_DIR`) and the Lua shadowenv (a brew `opt/` bin) already perform.

**Decision.**

- **The verb follows the upstream channel.** OS state (packages, users, kernel, daemons) is provisioning — the base image's Dockerfile, `dev-box-setup`, a bring-up block — not declared, not locked, not installed or verified by `dev up`; the gap is accepted knowingly (D4 of plans#50: native builds trade hermeticity for warmth; reopen on OS drift breaking a build). A package under a language runtime takes that runtime's verb. A thing a supported channel carries takes that channel's verb, including when a release we own also carries it.
- **A new verb needs a channel that passes the admission test**: an enumerable or addressable universe; immutable published versions; integrity dev verifies or the tool enforces from the lock; an install dev probes per host without root. Passing and supported: `brew`/`cask`, `gem`, `pip`, `luarocks`, `gh`, `cmake`, `steam`, `ficsit`. `xcode` and `wwise` are admitted under a relaxed test (addressable, not enumerable) because their artifacts cannot be re-hosted, so no stricter channel can exist for them. Failing: `apt`/dnf, snap, winget, floating docker tags, docker images as a dependency carrier. Candidates on demand, all passing: cargo, npm, nix, conda/pixi.
- **Repackaging into a channel we own needs one of three triggers**, named in the formula or release: no channel exists (the engine, MSVC under Wine, Ruby); a channel exists but fails admission (Wine via apt); we change the bytes. Which own channel follows need: a brew formula and bottle when there are transitive runtime dependencies to declare; a `gh` release when self-contained, large or licensed; source when the build wants it. A thin lift of what a supported channel carries is a stopgap naming its retirement condition. Sugar verbs (`ruby`, `python`) are coupling plus activation and mint a declaration in a real channel underneath.
- **Brew stays the cross-platform binary channel for anything with transitive runtime dependencies**, because `depends_on` declares and installs the closure a bare tree cannot, and pinning (ADR-0003), bottle sets (ADR-0004), carry-over (ADR-0005) and the store's bottle cache are built. Its two defects as used are gaps in dev, closed by dev: `BrewIntegration` activates `Cellar/<formula>/<locked version>/bin` through the project shadowenv, so two projects locking two versions each run their own and `verify_installed!`'s any-keg rule becomes exactly right; dev owns retention for locked formulae (`brew pin`, `HOMEBREW_NO_CLEANUP_FORMULAE`), making ADR-0003 B a check rather than the only defence ([dev#289](https://github.com/d3mlabs/dev/issues/289)). `gh` trees carry self-contained publisher artifacts and activate the same way.
- **Tap admission** (homebrew-d3mlabs README): software we author; repackages only under a trigger, bottled for arm64 macOS and x86_64 Linux by the tap's CI; thin lifts only as stopgaps naming their retirement; `name@exact` when concurrent versions across projects are plausible; every formula names the trigger that admitted it.

**Consequences.** `ruby` and `python` mint declarations that resolve and install as brew pins — `ruby` against the tap's `ruby@X.Y.Z` family, `python` against homebrew/core's `python@<minor>` (ADR-0012, dev#269); the ruby-build path and `ContainerRuby` go. A new need is answered by the flowchart in deps-channels.md before any code: most often an existing verb, sometimes a new channel at roughly five classes once, rarely a formula. Remaining brew costs accepted: our tap's bottles need our CI per platform; Linuxbrew bottles are x86_64 only; kegs live in the brew prefix, so persistence covers two directories. The three thin lifts retire once `gh` trees activate ([homebrew-d3mlabs#6](https://github.com/d3mlabs/homebrew-d3mlabs/issues/6)).

**Rejected.** *A verb per kind of thing* (a `:ruby` integration, an `apt` type) — a dependency class per package with an installer each, re-earning what a channel already has; dev#284's withdrawal and dev#269's re-body are this rejection applied. *Repackage by default into the tap* — right for Ruby by the no-channel trigger, wrong as a rule: a formula per upstream release times platforms, forever, against a channel's one-time cost. *`gh` trees for everything we publish* — store-native, gc by lock, but no transitive runtime dependencies: for Ruby it re-invents `depends_on`. *Keg-only formulae as the coexistence mechanism* — brew's native form, unnecessary once dev activates the locked keg, and nothing for core formulae. *nix as the universal lockable channel* — would delete most of dev's dependency layer (`flake.lock` for ADR-0003/4/5, `/nix/store` for the data root, a binary cache for the publisher pattern) and closes the OS gap only for what nix builds; a second package manager, team and agent expertise, macOS fragility, a private cache to run; a migration to start if starting now, not mid-flight. Reopen if a second project needs hermetic Linux builds on workstations or OS drift breaks a build. *Always-container* (every build inside the base image, hosts included) — hermetic, but a Linux host already is the environment's platform (ADR-0007) and it would move every data root behind a VM boundary on a Mac (ADR-0008's measurement).

**Note (2026-10-25, [dev#277](https://github.com/d3mlabs/dev/issues/277)).** The OS-state gap closes for the part of it dev can see: a project declares its build environment as an `image` block in `dependencies.rb` — a floor (`from:` a base image dev's org publishes, resolved to its registry digest), a `platform`, and the `apt` packages the project needs on top — and **the image is the pin**. dev generates the Dockerfile (the floor by digest, one apt layer, dev's contract: Linuxbrew on PATH, `builder`, `/project`, a marker at `/etc/dev/environment`), and the lock records the floor digest, the platform, the sorted apt set and the SHA-256 of that text, which is also the registry tag: a change to the floor, a package, or dev's template is a reviewed lock diff and a new image; two devs that compute different digests for one lock refuse to run (`dev deps update` cures it). The image stays what ADR-0001 and this decision said: OS state, not a dependency carrier — nothing from the lock enters it, the container's `dev deps install` installs the lock inside (ADR-0002). `apt` is admitted only there, as the apt layer of the generated Dockerfile, never as a verb: the floor's own packages are the floor publisher's, and a `brew`-carried tool is still `brew`. The registry credential is the host's `gh auth` (read or write `packages` scope) — or, when the registry will not take that identity, the token `DEV_REGISTRY_TOKEN` names ([dev#351](https://github.com/d3mlabs/dev/issues/351): GHCR refuses GitHub App installation tokens, which hosted jobs hold for the private releases, and accepts the job's own `GITHUB_TOKEN`) — entered by dev around the one operation that needs it and left nowhere — not a workflow login step, not a bring-up `docker login`, not a `DOCKERHUB_*` secret. What stays provisioning: the floor image itself (its publisher's Dockerfile), users, kernel, daemons, and a host that *is* the environment (ADR-0007), where `dev-box-setup` and the bring-up block remain the whole answer. The hand-written-Dockerfile path (`build.container.image/registry`, `content-<hash>` tags, prewarm, build secrets) is deprecated and goes with [dev#311](https://github.com/d3mlabs/dev/issues/311) once cellbound-3d and snappy have migrated.

**Note (2026-10-23, dev#289).** Retention is `HOMEBREW_NO_CLEANUP_FORMULAE` alone, written to the user's `brew.env` after every install; `brew pin` is dropped. A pin makes `brew upgrade <formula>` refuse, which is ADR-0003 B's remediation when a lock is ahead of the keg, and brew itself warns that dependents of a pinned formula may not install or run — owning that on a workstation is what ADR-0003 declined. With the locked keg activated per project, a pin buys nothing: a bulk `brew upgrade` adds a keg and relinks, no-cleanup keeps the old keg, and the project's PATH never moved. The no-cleanup list only grows; releasing a name needs the cross-project view of dev#286. When brew writes are escalated to another prefix owner (plans#26), dev leaves that owner's `brew.env` alone and says so.

## ADR-0011 — Groups are purpose-only; integrations carry their own manifest; one lockfile

**Status:** Accepted. Decision 3 of [plans#50](https://github.com/d3mlabs/plans/issues/50) (2026-10-23). Lands in [dev#274](https://github.com/d3mlabs/dev/issues/274) through [dev#290](https://github.com/d3mlabs/dev/issues/290) (stage 1, merged 2026-10-24) and [dev#293](https://github.com/d3mlabs/dev/issues/293) (one lockfile); stage 2 is [dev#291](https://github.com/d3mlabs/dev/issues/291), the integration SPI [dev#300](https://github.com/d3mlabs/dev/issues/300), stage 3 [dev#292](https://github.com/d3mlabs/dev/issues/292) — additive.

**Context.** The `build` group carried four jobs: purpose (which consumer role wants it — legitimate), installer ordering (the build-first partition in `installer.rb`, whose own comment calls it a stand-in for a topological sort), image membership (retired by ADR-0008: no lock is an image input), and a separate `build-deps.lock` whose stated reason — `hashFiles('build-deps.lock')` as the content-addressed image's cache key — retired with it. The ordering job is why `XcodeIntegration` and `WwiseIntegration` tell the consumer to declare `xcodes` and `wwise-cli` in `:build`, while `gh`, `git`, `rbenv` and `shadowenv` — the tools other integrations shell to — are `dev-core`'s `depends_on`: dev's own tooling in two places, neither right. Meanwhile `gh "MsvcWineToolchain" … tag: "toolchain-2"` is declared verbatim in cellbound-3d and unreal-engine, a fact that belongs to the engine release and is enforced only by the tree's `MANIFEST` and a verify step. In mature managers "build" is a platform fact (cargo `[build-dependencies]`, nix `nativeBuildInputs`), which `host:` already carries; groups' lasting purpose is selection by role, as bundler groups and npm dev dependencies.

**Decision.**

- **Groups are purpose-only.** `--group`/`--except` selection; nothing installs first because of its group name.
- **An integration carries one `dependencies.rb` of its own**, in the project DSL (`brew "xcodes"`; `brew "wwise-cli", tap: "d3mlabs/d3mlabs"`; `gem` lines for its Ruby). When a project's manifest uses the integration, dev resolves that manifest into the **project's lock** as ordinary pins in their channel with provenance (`needed_by: xcode`), in the using declaration's scope — the Resolver's existing walk of a `Resolved` declarations claim with scope inheritance (ficsit today), with the integration as parent. A project also declaring the tool merges through `ConflictingDeclarationError`. `dev-core`'s `depends_on` shrinks to dev's own runtime.
- **Export rule, the Gemfile/gemspec convention for every verb:** ungrouped declarations export to the consumer; grouped ones are private; a library declares ranges and the project locks; a dependency's `deps.lock` is never read; `ruby`, `python` and `env` never propagate. A library-mode validation enforces it. The same walk reads a `gh` dependency's `dependencies.rb` at the chosen tag (stage 2): the engine exports its toolchain pin, cellbound-3d declares the engine alone, and an exact-pin disagreement is `ConflictingDeclarationError` — the verify step made structural. Range intersection waits for a scheme algebra behind deps-architecture.md's decision gate.
- **Ownership says where code loads from, nothing else.** Built in, in a project's own folder, or a gem: the same class shape, manifest and resolution. An integration is a dependency: what marks a dependency (or the project itself) as providing one is an `integration "<path>"` line in its *own* `dependencies.rb`, pointing at a file that calls `Dev::Deps.register(Entry)`; declarations whose verb is not yet bound wait until the provider is installed and loaded ([dev#300](https://github.com/d3mlabs/dev/issues/300)). A gem-packaged integration authors one `dependencies.rb` and dev derives the gemspec's dependency list from its ungrouped `gem` lines. wwise is extracted as the first (stage 3); xcode stays built in, its needs installing only for a project that pins an Xcode.
- **The installer orders by the graph.** An integration's needs are pins of other integrations and install first; brew is the host prerequisite; bundler-after-Ruby and pip-after-Python are the same edges; a cycle is refused loudly. The build-first partition goes.
- **One lockfile**, `deps.lock`, nested by integration, every group in it. `build-deps.lock` is no longer written or read.

**Consequences.** A breaking minor (ADR-0001) shipped as dev#274 with consumers (cellbound-3d, unreal-engine, snappy) re-locking in lockstep: two `brew` lines leave each consumer manifest with lock content unchanged but provenance added; `build-deps.lock` is deleted at re-lock; the checkpoint gate watches `deps.lock`, `Gemfile.lock` and `.ruby-version`; `TapCommitCarryover` has one input. Stage 2 adds one API call per `gh` dependency at its selected tag only. Extraction of an integration becomes moving a file, which is the precondition for project-local and shared integrations.

**Rejected.** *A three-tier ownership rule* (built-in tooling in `dev-core`, project-local in the project's manifest, shared "later") — three places for one fact, `xcodes` and `wwise-cli` on every machine, extraction left as a redesign. *A `needs` block on the Integration class* — the same walk with the manifest elsewhere, and it does not generalise to a dependency's manifest. *A gemspec for Ruby deps plus `dependencies.rb` for machine needs* — two authored sources for one library, against dev's stance that projects author `gem` lines and never a Gemfile; the gemspec stays as a derived artifact because the gem format requires it. *Deferring transitive manifests* — the position until the export semantics and library conventions had homes; both are the Gemfile/gemspec conventions already in force, and the walk exists, so stage 1 needs nothing new and staging keeps 2 and 3 from blocking it. *Declaration order in `dependencies.rb` as the ordering* — the manifest is declarative, resolved to a lock nested by integration with order discarded, and `Installer#dispatch` batches per integration. *"`:build` installs first" as a documented convention* — keeps dev's tooling in consumer manifests. *Two lockfiles* — a key no consumer uses, at the cost of a second carry-over path and gate entry.

## ADR-0012 — The interpreters are brew pins

**Status:** Accepted. Decision 1 of [plans#50](https://github.com/d3mlabs/plans/issues/50) applied to Ruby and Python; lands in [dev#269](https://github.com/d3mlabs/dev/issues/269), the tap side in [homebrew-d3mlabs#8](https://github.com/d3mlabs/homebrew-d3mlabs/issues/8).

**Context.** The project Ruby was the one dependency outside the dependency system: `ruby "4.0.6"` in `dependencies.rb` was read by every command through a side channel (`Config#ruby_version_requirement` → `ProjectManifest` → `ProjectContext` → `CommandRunner`), which compiled it with rbenv/ruby-build on the host — two to three minutes per host, a growing list of brew build libraries and configure flags, a compiler choice on old-glibc Linuxbrew, and two verification guards for the ways a compiled ruby silently came out wrong (a skipped extension, a libruby hijack by a same-minor sibling, dev#75, dev#204) — and again, differently, inside the build container (`ContainerRuby`: a ruby-build tree in the artifact store, a marker-gated second lisp). Python had the same shape with less of it: `python "3.12"` → `brew install python@3.12` from a pre-dispatch step, the venv built by whoever got there first (`CommandRunner` or `PipIntegration`). Neither was locked: `.ruby-version` was the only record, and nothing pinned the Python patch at all. ADR-0010 settled the channel question — Ruby has no channel and is repackaged into the tap under the no-channel trigger; Python has one, homebrew/core — and left the implementation to this decision.

**Decision.**

- **`ruby` and `python` are sugar verbs over `brew`.** Each mints a declaration of its own type (`:ruby`, `:python`) so the lock reads `ruby:` / `python:` and the resolver can give each its own version semantics, and each installs as a brew pin: `install_alias: :brew` in the registry — the same `BrewIntegration` instance, in brew's batch, the host prerequisite that installs first. No integration class, no lifecycle of their own.
- **`:ruby` resolves over the tap's `ruby@X.Y.Z` family with rubygems semantics.** The d3mlabs tap publishes one immutable, keg-only `ruby@X.Y.Z` formula per Ruby patch, bottled for arm64 macOS and x86_64 Linux. `BrewRepository` enumerates a tap formula's family from the tap's own formula list (`brew tap-info --json`; brew reports `versioned_formulae: []` for third-party taps, and the family has no bare member), each member's `version_suffix` being its exact version, and `GemScheme` selects: `"4.0.6"` pins, `"~> 4.0"` takes the highest 4.0.x the tap has today, a bare minor `"4.0"` is `"~> 4.0.0"`. A patch upgrade is a re-lock.
- **`:python` selects homebrew/core's `python@<minor>`** through `BrewScheme`, the minor being the formula suffix exactly as `brew "llvm", version: "18"` selects `llvm@18`. The lock carries the formula's version as brew reports it.
- **Activation rides the install.** After `BrewIntegration` puts the locked kegs' `bin` on the project PATH (`515_brew.lisp`, ADR-0010), it hands each interpreter's keg to its language activation: `ShadowenvRuby.activate!` writes `510_ruby.lisp` (`RUBY_ROOT`; `GEM_HOME` is the keg's own gem dir, never a version-keyed `~/.gem` — a native extension links the libruby that built it, and a keg beside an earlier rbenv build of the same version must not share its gems) and `.ruby-version`; `ShadowenvPython.activate!` builds the project `.venv` on the keg — rebuilt when the existing venv was built on another interpreter — and writes `540_python.lisp`. These modules install nothing. `Dev::ShadowenvFile` places every activation lisp for the side of the build container that wrote it (a `_container` sibling gated on the inside marker), generalising what `ContainerRuby` did for its own file so the bind-mounted `.shadowenv.d/` keeps serving both sides.
- **`dev deps update` installs the interpreters before the lockers run.** The interpreter declarations are resolved and installed first, so `BundlerLocker` receives the locked exact Ruby for the generated Gemfile's `ruby` directive and `bundle lock` runs under it; then the full resolve, the lock. `dev deps install` is a plain install. No command provisions an interpreter: the side channel — `Config`, `ProjectManifest`, `ProjectContext`, `ExecutionContext`, the loader's `dependencies.rb` pass, `CommandRunner`'s pre-dispatch, `Runner`'s Homebrew-Ruby fallback — is gone, and `dependencies.rb` is evaluated only by the deps commands. `PipIntegration` installs into the venv the `python` pin's activation built and refuses when there is none.
- **A project that declares no `ruby` gets none.** Its commands run under whatever Ruby the shell has; dev itself needs none of the project's (its trampoline runs on Homebrew Ruby).

**Consequences.** A `dev up` on a fresh host pours a bottle instead of compiling; the guards against a miscompiled ruby, the build-library list and the compiler selection are deleted with the compile. The lock pins the Ruby patch and the Python formula version like any dependency, so two projects on two patches coexist (ADR-0010's keg activation) and a patch bump is a reviewed lock diff. Inside the container the Ruby is the same bottle in the Linuxbrew volume; `ContainerRuby`, `RubyBuild` and the store's ruby and gem trees go. Consumers re-lock (cellbound-3d, unreal-engine, snappy — alongside dev#274), and `dev-core`'s `depends_on rbenv` / `ruby-build` retires in the tap. A tap patch missing from the family is a `NoSatisfyingVersionError` at `dev deps update`, remedied by publishing the formula ([homebrew-d3mlabs](https://github.com/d3mlabs/homebrew-d3mlabs)) — the price of a channel we own. The `.venv` stays in the project root and so is shared with the container; `venv_built_on?` keeps it correct for whichever side installed last, at the cost of a rebuild when sides alternate — the per-side venv is a follow-up.

**Rejected.** *A `:ruby` integration with a ruby-build install path* (dev#269's first body) — a dependency class with its own installer, re-earning transitive deps, bottles, pinning and retention that brew has (ADR-0010's rejection applied). *A bare `ruby` formula with `versioned_formulae`* — brew enumerates the family only for core formulae, and a bare, mutable `ruby` in the tap is a floating pin; the family is read from the tap's formula list instead. *Keeping `.ruby-version` as the pin* — the standard file stays as generated output for tools that read it, but the lock is the record: the file carries no integrity facts and no platform bottles. *Resolving the Ruby late, in `CommandRunner`, from the lock* — every command would read the lock to find a keg the install already activated; activation at install time is the uniform rule (ADR-0010). *Container-only install of the interpreter from the image* — the image is OS state, not a dependency carrier (ADR-0001, ADR-0010); the container's Ruby is a dependency the container's `dev deps install` installs where it is consumed (ADR-0002).
